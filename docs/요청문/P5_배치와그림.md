# P5 요청문 — 배치와 그림(Neo4j식 배치 계산 · 원 겹침 막기 · 배치 좌표 기준 크기 · 직선 · 이름 자리)

> **수신**: 플랫폼 구현 세션 · **발신**: 플랫폼 트랙 (2026-11-19 · 사용자 확정) · **P4(PR #5) 병합 뒤**
> **근거**: `docs/명세.md` §5.1 배치 · §5.2 그림 · §4 `/api/graph` · §8 2026-11-19
> **시스템 기준 커밋**: `playjae0/ontology_system` `5ae4444` — 읽기 전용. 개발 환경은 P3 §0 그대로(mock 73노드 · 합성은 `verify/p3_synth.py`).
> **시간**: 두 시간을 넘기지 않는다. 넘을 것 같으면 완료판정 순서대로 된 데까지 하고 멈춰서 보고한다 — ⓐ~ⓓ(배치 · 끌기 · 자리 잡기 · 직선)가 먼저다.

**왜 하는가.** 사용자가 사내에서 처음 켜 보고(2026-11-18) 「시스템 뷰어를 조금 바꾼 수준」이라고 했다. 원한 것은 구 플랫폼(`ontology_platform` · NVL)처럼
Neo4j와 거의 같은 시각화다 — 지금은 노드가 서로 멀어지지 않고, 선이 직선과 곡선으로 섞이고, 다시 배치해도 잘 따라오지 않는다. 홉 탐색은 좋고 부하는 크지 않다.
원인은 그리기와 배치를 시스템 뷰어에서 옮긴 데 있다 — ① ForceAtlas2는 비슷한 것끼리 뭉치게 하는 계산이라(허브가 잎을 끌어당기고 전체를 가운데로 당긴다)
간격을 키워도 뭉침이 남는다 ② 원 크기가 화면 픽셀 기준이라 화면 맞춤에서 원끼리 겹치고 배치 좌표와 따로 논다 ③ 층을 건너는 선만 곡선이다. NVL은 라이선스로 쓸 수 없다(명세 §8).
**이 회차가 하는 것**: 배치 계산을 Neo4j 방식(쉬는 길이 용수철 · 밀어냄 · 겹침 막기 · 약한 당김)으로 바꾸고, 원 크기를 배치 좌표 기준으로, 선을 전부 직선으로,
이름을 「들어가면 원 안 · 아니면 원 옆」으로 한다. **그대로 두는 것**: 끌기의 성질(연결된 것이 따라오고 먼 곳은 흐르지 않는다) · 홉 탐색 · 거르기 · 질의 · 상세 ·
워커 메시지와 `LayoutState` — 확인 스크립트가 이 손잡이로 잰다.

## 2. 만들 것

- **① 배치 계산**(명세 §5.1 [P5]) — `force_worker.js`를 d3-force로 다시 쓴다(`d3-force@3.0.0` · ISC · `package.json`에 판 고정 · 빌드에 묶여 들어간다 · 외부 주소 0).
  - 힘 넷: `forceLink`(쉬는 길이 = rₛ + rₜ + GAP · 세기는 d3 기본) · `forceManyBody`(세기 CHARGE · `distanceMax`) · `forceCollide`(반지름 r + PAD) · `forceX`/`forceY`(0을 향해 세기 CENTER).
  - 라이브러리 타이머는 쓰지 않는다 — `simulation.stop()` 뒤 워커가 `tick()`을 직접 돈다. 반복 수로 센다(전체 배치는 LAYOUT_TICKS — 그 반복에서 alpha가 `alphaMin`에 닿도록
    `alphaDecay`를 정한다) · 프레임은 지금처럼 몇 반복마다 하나 · 결정적이다(d3-force 3의 고정 시드 난수 · 같은 시작 자리 · 같은 반복 수).
  - 워커 메시지(`start · stop · resume · pin · cool`)와 `frame {x, y, iter, max, done, ms}` · `ForceLayout`의 바깥 함수(`start · startDrag · startSettle · release · pause · pin`) ·
    `LayoutState`(kind · running · paused · iterations · max)는 그대로 둔다 — p1 · p15 · p16 · p3 · p4가 이 손잡이로 잰다.
  - 상수는 `force.ts` 한 자리. 처음 값(가결정 — ⓐ의 성질을 맞추려고만 바꾸고, 바꾸면 `DECISIONS.md`에 까닭):
    R_MIN 12 · R_MAX 30(원 반지름 · 배치 단위) · GAP 60 · PAD 4 · CHARGE −300 · `distanceMax` 800 · CENTER 0.02 · LAYOUT_TICKS 400 · COOL_ITER 300(그대로) · `velocityDecay` 0.4(d3 기본).
    mock 표본의 모양에 맞춰 고르지 않는다(명세 §2-5) — 사내 결과로 맞춘다(명세 §7.1).
  - 시작 자리: `seed.ts`는 그대로 두고 좌표에 배율 하나(2·R_MIN + GAP)를 곱한다.
  - 「간격」 배수 s(밀대 그대로): 쉬는 길이 전체 × s · CHARGE × s²(명세 §5.1 조절) — 바꾸면 지금처럼 지금 자리에서 전체 배치로 다시 돈다(DECISIONS P-06).
  - `/api/graph`의 `force`는 쓰지 않는다 — `view.ts`의 읽기를 빼고 `backend/contract.py`의 칸 목록에서도 뺀다(명세 §4).
- **② 끌기**(명세 §5.1 끌기 배치) — 같은 성질을 d3 방식으로.
  - 끄는 노드는 `fx`·`fy`로 손에 고정 · 누르는 동안 `alphaTarget` 0.3으로 데운다 · 놓으면 `alphaTarget` 0 + `cool`(COOL_ITER) · 놓은 노드는 고정 그대로(지금과 같다).
  - 붙잡기 힘(사용자 힘 하나): `vᵢ += α · kᵢ · (제자리ᵢ − xᵢ)` · kᵢ = 지금의 `springOf(h, k₀)` 그대로(질량은 곱하지 않는다 — d3에는 질량이 없다).
  - 제자리 = 시작 순간 다른 힘의 합을 상쇄하는 자리(B-01과 같은 원리): 속도를 0으로 두고 다른 힘을 α = 1로 한 번 돌려 얻은 속도 변화를 Fᵢ라 하면 제자리ᵢ = xᵢ − Fᵢ / kᵢ
    (고정점 · kᵢ = 0은 지금 자리). 끄는 노드에서 닿지 않는 노드는 그 끌기 동안 고정 · 「멈춤」 중 끌기는 그 점만 옮긴다(지금과 같다).
- **③ 자리 잡기**(명세 §5.1 보이는 노드가 바뀔 때) — P3 규칙 그대로 새 계산으로: 새 노드는 host 둘레 고리(지금 코드) · 이미 있던 노드는 붙잡기 힘 SETTLE_SPRING(1) ·
  새 노드는 0 · 끌기와 같은 alpha 0.3에서 COOL_ITER만큼 식는다 · 새 노드 > 이미 있던 노드면 전체 배치 · 빠질 때는 빠지기만(다시 데우지 않는다).
- **④ 선**(명세 §5.2 엣지) — 전부 직선 화살표(`arrow`). 층을 건너는 선은 색 `COLOR.cross` · 굵기 1.6으로만 가른다. `@sigma/edge-curve`를 쓰지 않게 되면 `package.json`에서도 뺀다.
- **⑤ 크기**(명세 §5.2 크기) — sigma `itemSizesReference: "positions"` · `zoomToSizeRatioFunction: (r) => r` — 원 크기가 배치 단위가 되어 확대하면 같은 비율로 커진다.
  반지름 = R_MIN + (R_MAX − R_MIN) × √(연결 수 ÷ 최대 연결 수) — 그리는 원과 겹침 막기가 같은 값을 쓴다(`style.ts` 한 자리). 엣지가 너무 가늘어지면 sigma `minEdgeThickness`로만 받친다.
  찾기 강조의 「+4」처럼 크기에 더하는 값은 배치 단위에 맞게 비율로 바꾼다.
- **⑥ 이름 자리**(명세 §5.2 라벨) — `drawLabel` 하나에서 고른다: 그린 원의 화면 지름 ≥ 글자 폭 + 8px이고 반지름 ≥ 12px이면 원 안 가운데(글자 크기는 반지름에 비례해 10~16px ·
  글자색은 원 색의 밝기로 검정이나 흰색) · 아니면 지금처럼 원 옆(tier 계단 글자 크기). 확인용 손잡이에 마지막 그리기의 원 안 · 원 옆 수(`window.__platform.labels`).
- **장부**: DECISIONS P-54부터 · PROGRESS 맨 위.
